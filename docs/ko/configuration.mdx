## 필드 참조

### `repository`

`PATCH /repos/{owner}/{repo}`를 통해 적용되는 표준 GitHub 리포지토리 설정입니다. 각 키는 GitHub API 필드에 직접 매핑됩니다. [설정 적용 워크플로](./settings-enforcement/)는 각 키를 리포지토리의 현재 값과 비교하고 드리프트된 키만 패치합니다.

주요 설정:

- `delete_branch_on_merge: true` -- 병합된 PR 브랜치를 자동으로 정리합니다.
- `allow_update_branch: true` -- PR에서 "Update branch" 버튼을 활성화합니다.
- `homepage: ""` -- 실행 시 `https://f5-sales-demo.github.io/{repo}/`로 자동 계산됩니다.

### `actions_permissions`

리포지토리의 GitHub Actions 워크플로 권한을 제어합니다.

- `default_workflow_permissions: "write"` -- 워크플로는 기본적으로 리포지토리에 대한 읽기/쓰기 권한을 얻습니다.
- `can_approve_pull_request_reviews: true` -- 워크플로가 PR을 승인할 수 있도록 허용합니다.

### `branch_protection`

브랜치 보호 규칙의 배열입니다. 각 항목은 `branch` 이름과 원하는 보호 설정을 지정합니다. 현재는 `main`만 보호됩니다.

주요 필드:

- `enforce_admins: true` -- 보호 규칙이 리포지토리 관리자에게도 적용됩니다.
- `required_status_checks.strict: false` -- 병합 전에 브랜치가 최신 상태일 필요는 없습니다.
- `required_status_checks.contexts` -- 다운스트림 리포지토리가 통과해야 하는 검사 이름(예: `check / Check linked issues` 및 `lint / Shell Unit Tests`)
- `required_status_checks.self_contexts` -- docs-control 자체가 통과해야 하는 검사 이름(예: `Check linked issues` 및 `Shell Unit Tests`)
- `required_pull_request_reviews: null` -- PR 검토 승인이 필요하지 않습니다.
- `restrictions: null` -- 브랜치 보호 이외의 푸시 제한이 없습니다.

#### `contexts` 대 `self_contexts`

다운스트림 리포지토리가 호출자 워크플로를 사용할 때 상태 검사 이름은 `<caller_job_key> / <reusable_job_name>`이 됩니다. 예를 들어 `require-linked-issue.yml` 호출자의 작업 키는 `check`이므로 검사 이름은 `check / Check linked issues`가 됩니다. 그러나 docs-control이 동일한 워크플로를 직접 실행할 때(`pull_request_target` 트리거를 통해), 검사 이름은 단지 `Check linked issues`가 됩니다.

`self_contexts` 필드는 docs-control 자체에 적용되는 검사 이름을 저장합니다. [적용](./settings-enforcement/) 중에 워크플로는 소스 리포지토리에서 실행 중인지 감지하고 브랜치 보호를 적용하기 전에 `self_contexts`를 `contexts`로 교체합니다. `self_contexts` 필드는 GitHub API에 페이로드를 전송하기 전에 항상 제거됩니다.

`Shell Unit Tests`는 통일된 리포지토리 테스트 게이트입니다. 재사용 가능한 워크플로는 항상 이를 보고합니다. 소비 리포지토리는 모든 `tests/test-*.sh` 파일을 실행하며, 일치하는 테스트가 없는 리포지토리는 명시적인 테스트 없음 메시지와 함께 성공을 보고합니다. 이를 통해 리포지토리별 옵트인 목록에 의존하는 대신 리포지토리 셸 테스트가 기본적으로 필수 항목이 됩니다.

#### 소비 셸 테스트 프로필

기본값은 모든 루트 수준 `tests/test-*.sh` 스크립트가 프로비저닝되지 않은 GitHub 호스팅 러너에서 밀폐되어(hermetic) 있다고 가정합니다. 해당 글로브에 컨테이너 또는 서비스 통합 테스트도 저장하는 리포지토리는 `repo-settings.json`에 `consumer_shell_tests.profiles` 항목이 필요합니다.

각 프로필은 일치하는 전체 인벤토리를 분류합니다.

- `unit` 항목에는 테스트 `path` 및 `args` 배열이 포함됩니다. 러너는 셸 평가 없이 각 인수를 그대로 전달합니다.
- `environment` 항목에는 테스트 `path` 및 베어 러너 단위 게이트에서 실행할 수 없는 이유를 설명하는 비어 있지 않은 `reason`이 포함됩니다.

재사용 가능한 워크플로는 동일한 docs-control `main` 개정판에서 선택기와 구성을 가져오고 해당 개정판을 기록하며 아무것도 실행하기 전에 인벤토리를 검증합니다. 누락된 구성, 안전하지 않은 경로나 인수, 중복된 경로, 미분류되거나 누락된 테스트는 필수 컨텍스트를 실패하게 만듭니다. 이를 통해 프로필은 무시 목록이 아니라 감사된 분류 계약이 됩니다. 프로필이 없는 리포지토리는 광범위한 기본값을 유지합니다.

`xcsh` 재정의는 해당 리포지토리가 재사용 가능한 Super-Linter 워크플로를 호출하지 않기 때문에 두 Super-Linter 컨텍스트를 모두 제외합니다. 네이티브 `check`, `pii-guard` 및 `test` 컨텍스트는 계속 필요합니다. 라이브 검증을 통해 제외가 필요함이 입증된 후에만 추가되어야 합니다.

`paths` 또는 `paths-ignore` 필터가 있는 워크플로의 컨텍스트를 필수 항목으로 지정하지 마세요. 워크플로가 시작되지 않을 때 GitHub는 해당 컨텍스트를 보류 상태로 둡니다. 광범위한 보안 도구는 필터링되지 않은 풀 리퀘스트 워크플로 또는 예약된 전체 트리 감사에서 실행되어야 합니다. 관리되는 워크플로 보안 감사는 `zizmor`에 대해 후자의 모델을 사용합니다. 건너뛴 작업도 성공적인 검사를 보고하므로 작업 수준 조건은 안전합니다.

### `topics`

리포지토리에 적용할 GitHub 토픽의 배열입니다. 현재 비어 있음 -- 토픽은 강제되지 않습니다.

### `pages`

GitHub Pages 구성:

- `enabled: true` -- 등록된 모든 리포지토리에서 Pages가 활성화되어 있는지 확인합니다.
- `build_type: "workflow"` -- Pages 빌드에 GitHub Actions를 사용합니다(기존 브랜치 기반 빌드가 아님).

### `managed_files`

파일 동기화 매니페스트를 정의합니다.

- `source_repo` -- 관리 대상 파일의 정식 버전을 보유하는 리포지토리(`f5-sales-demo/docs-control`)
- `files` -- docs-control의 소스 경로를 다운스트림 리포지토리의 대상 경로에 매핑하는 `{src, dest}` 개체의 배열

[파일 동기화 워크플로](./file-sync/)는 이 배열을 순회하여 드리프트를 감지하고 수정합니다. 여기에 나열되지 않은 파일(`dependabot.yml` 및 `README.md` 등)은 정적 소스에서 동기화되는 대신 동적으로 생성됩니다.
