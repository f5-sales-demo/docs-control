## फ़ील्ड संदर्भ

### `repository`

`PATCH /repos/{owner}/{repo}` के माध्यम से लागू की गई मानक GitHub रिपॉजिटरी सेटिंग्स। प्रत्येक कुंजी सीधे GitHub API फ़ील्ड से मैप होती है। [एनफ़ोर्समेंट वर्कफ़्लो](./settings-enforcement/) रिपॉजिटरी के वर्तमान मूल्य के खिलाफ प्रत्येक कुंजी की तुलना करता है और केवल उन्हीं कुंजियों को पैच करता है जो ड्रिफ्ट हुई हैं।

प्रमुख सेटिंग्स:

- `delete_branch_on_merge: true` -- मर्ज की गई PR ब्रांचों को स्वचालित रूप से साफ़ करता है
- `allow_update_branch: true` -- PRs पर "Update branch" बटन को सक्षम करता है
- `homepage: ""` -- रनटाइम पर `https://f5-sales-demo.github.io/{repo}/` के रूप में ऑटो-कंप्यूट किया जाता है

### `actions_permissions`

रिपॉजिटरी के लिए GitHub Actions वर्कफ़्लो अनुमतियों को नियंत्रित करता है:

- `default_workflow_permissions: "write"` -- वर्कफ़्लो को डिफ़ॉल्ट रूप से रिपॉजिटरी के लिए पढ़ने/लिखने की पहुंच मिलती है
- `can_approve_pull_request_reviews: true` -- वर्कफ़्लो को PRs को स्वीकृत करने की अनुमति देता है

### `branch_protection`

ब्रांच प्रोटेक्शन नियमों का एक सरणी (array)। प्रत्येक प्रविष्टि एक `branch` नाम और वांछित सुरक्षा सेटिंग्स निर्दिष्ट करती है। वर्तमान में केवल `main` सुरक्षित है।

मुख्य फ़ील्ड:

- `enforce_admins: true` -- सुरक्षा नियम रिपॉजिटरी प्रशासकों पर भी लागू होते हैं
- `required_status_checks.strict: false` -- मर्ज करने से पहले ब्रांचों को अप-टू-डेट होने की आवश्यकता नहीं है
- `required_status_checks.contexts` -- चेक नाम जिन्हें डाउनस्ट्रीम रिपॉजिटरी को पास करना होगा (उदाहरण के लिए, `check / Check linked issues` और `lint / Shell Unit Tests`)
- `required_status_checks.self_contexts` -- चेक नाम जिन्हें स्वयं docs-control को पास करना होगा (उदाहरण के लिए, `Check linked issues` और `Shell Unit Tests`)
- `required_pull_request_reviews: null` -- किसी PR रिव्यू अनुमोदन की आवश्यकता नहीं है
- `restrictions: null` -- ब्रांच प्रोटेक्शन से परे कोई पुश प्रतिबंध नहीं

#### `contexts` बनाम `self_contexts`

जब कोई डाउनस्ट्रीम रिपॉजिटरी कॉलर वर्कफ़्लो का उपयोग करती है, तो स्टेटस चेक नाम `<caller_job_key> / <reusable_job_name>` बन जाता है। उदाहरण के लिए, `require-linked-issue.yml` कॉलर के पास जॉब कुंजी `check` है, इसलिए चेक नाम `check / Check linked issues` है। लेकिन जब docs-control सीधे एक ही वर्कफ़्लो चलाता है (`pull_request_target` ट्रिगर के माध्यम से), तो चेक नाम केवल `Check linked issues` होता है।

`self_contexts` फ़ील्ड उन चेक नामों को संग्रहीत करता है जो स्वयं docs-control पर लागू होते हैं। [एनफ़ोर्समेंट](./settings-enforcement/) के दौरान, वर्कफ़्लो यह पहचानता है कि क्या यह सोर्स रिपॉजिटरी पर चल रहा है और ब्रांच प्रोटेक्शन लागू करने से पहले `self_contexts` को `contexts` में बदल देता है। GitHub API को पेलोड भेजने से पहले `self_contexts` फ़ील्ड हमेशा हटा दिया जाता है।

`Shell Unit Tests` एक समान रिपॉजिटरी-टेस्ट गेट है। रीयूज़ेबल वर्कफ़्लो हमेशा इसकी रिपोर्ट करता है: उपभोक्ता रिपॉजिटरी प्रत्येक `tests/test-*.sh` फ़ाइल चलाती है, जबकि बिना किसी मैचिंग टेस्ट वाली रिपॉजिटरी एक स्पष्ट नो-टेस्ट मैसेज के साथ सफलता की रिपोर्ट करती है। यह प्रति-रिपॉजिटरी ऑप्ट-इन सूचियों पर भरोसा करने के बजाय डिफ़ॉल्ट रूप से रिपॉजिटरी शेल परीक्षणों को आवश्यक बनाता है।

#### कंज्यूमर शेल-टेस्ट प्रोफ़ाइल

डिफ़ॉल्ट मानता है कि प्रत्येक रूट-लेवल `tests/test-*.sh` स्क्रिप्ट एक अनप्राविज़न्ड GitHub-होस्टेड रनर पर हर्मेटिक है। एक रिपॉजिटरी जो उस ग्लोब के तहत कंटेनर या सर्विस इंटीग्रेशन टेस्ट भी स्टोर करती है, उसे `repo-settings.json` में एक `consumer_shell_tests.profiles` प्रविष्टि की आवश्यकता होती है।

प्रत्येक प्रोफ़ाइल पूर्ण मिलान वाली इन्वेंट्री को वर्गीकृत करती है:

- `unit` प्रविष्टियों में एक टेस्ट `path` और एक `args` एरे शामिल होता है। रनर शेल मूल्यांकन के बिना, प्रत्येक तर्क को अक्षरशः पास करता है।
- `environment` प्रविष्टियों में एक टेस्ट `path` और एक गैर-खाली `reason` शामिल होता है जो यह बताता है कि बेयर-रनर यूनिट गेट इसे निष्पादित क्यों नहीं कर सकता।

रीयूज़ेबल वर्कफ़्लो उसी docs-control `main` रिविज़न से सेलेक्टर और कॉन्फ़िगरेशन प्राप्त करता है, उस रिविज़न को लॉग करता है, और कुछ भी चलाने से पहले इन्वेंट्री को सत्यापित करता है। गुम कॉन्फ़िगरेशन, असुरक्षित पथ या तर्क, डुप्लिकेट पथ, और अवगीकृत या गुम परीक्षण आवश्यक संदर्भ को विफल कर देते हैं। यह एक प्रोफ़ाइल को अनदेखा सूची के बजाय एक ऑडिट की गई वर्गीकरण अनुबंध बनाता है। बिना प्रोफ़ाइल वाली रिपॉजिटरी व्यापक डिफ़ॉल्ट को बनाए रखती हैं।

`xcsh` ओवरराइड दोनों Super-Linter contexts को बाहर करता है क्योंकि वह रिपॉजिटरी रीयूज़ेबल Super-Linter वर्कफ़्लो को कॉल नहीं करती है; इसके मूल `check`, `pii-guard`, और `test` contexts आवश्यक रहते हैं। लाइव सत्यापन को यह साबित करना होगा कि जोड़े जाने से पहले कोई अपवर्जन आवश्यक है।

`paths` या `paths-ignore` फ़िल्टर वाले वर्कफ़्लो से context की आवश्यकता न रखें। वर्कफ़्लो शुरू न होने पर GitHub उस context को पेंडिंग छोड़ देता है। व्यापक सुरक्षा उपकरणों को एक अनफ़िल्टर्ड पुल-रिक्वेस्ट वर्कफ़्लो में या एक निर्धारित पूर्ण-वृक्ष ऑडिट में चलना चाहिए; प्रबंधित वर्कफ़्लो-सुरक्षा ऑडिट `zizmor` के लिए उत्तरार्द्ध मॉडल का उपयोग करता है। जॉब-लेवल कंडीशन सुरक्षित है क्योंकि एक छोड़ी गई जॉब अभी भी एक सफल चेक की रिपोर्ट करती है।

### `topics`

रिपॉजिटरी पर लागू करने के लिए GitHub टॉपिक्स का एक एरे। वर्तमान में खाली -- टॉपिक्स लागू नहीं किए गए हैं।

### `pages`

GitHub Pages कॉन्फ़िगरेशन:

- `enabled: true` -- सुनिश्चित करता है कि प्रत्येक एनरोल की गई रिपॉजिटरी पर Pages सक्षम है
- `build_type: "workflow"` -- Pages बिल्ड के लिए GitHub Actions का उपयोग करता है (लेगेसी ब्रांच-आधारित बिल्ड का नहीं)

### `managed_files`

फ़ाइल सिंक्रनाइज़ेशन मैनिफ़ेस्ट को परिभाषित करता है:

- `source_repo` -- रिपॉजिटरी जो मैनेज्ड फ़ाइलों के प्रामाणिक संस्करण रखती है (`f5-sales-demo/docs-control`)
- `files` -- `{src, dest}` ऑब्जेक्ट्स का एक एरे जो docs-control में सोर्स पाथ को डाउनस्ट्रीम रिपॉजिटरी में डेस्टिनेशन पाथ से मैप करता है

[फ़ाइल सिंक वर्कफ़्लो](./file-sync/) ड्रिफ्ट का पता लगाने और उसे सही करने के लिए इस एरे को दोहराता है। यहां सूचीबद्ध नहीं की गई फ़ाइलें (जैसे `dependabot.yml` और `README.md`) स्थिर स्रोतों से सिंक किए जाने के बजाय डायनेमिक रूप से जेनरेट की जाती हैं।
