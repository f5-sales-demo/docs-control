## フィールドリファレンス

### `repository`

`PATCH /repos/{owner}/{repo}` を介して適用される標準の GitHub リポジトリ設定。各キーは GitHub API フィールドに直接マッピングされます。[設定適用ワークフロー](./settings-enforcement/) は、各キーをリポジトリの現在の値と比較し、ドリフトしたキーのみをパッチ適用します。

注目すべき設定:

- `delete_branch_on_merge: true` -- マージされた PR ブランチを自動的にクリーンアップします
- `allow_update_branch: true` -- PR 上の "Update branch" ボタンを有効にします
- `homepage: ""` -- 実行時に `https://f5-sales-demo.github.io/{repo}/` として自動計算されます

### `actions_permissions`

リポジトリの GitHub Actions ワークフロー権限を制御します:

- `default_workflow_permissions: "write"` -- ワークフローはデフォルトでリポジトリへの読み取り/書き込みアクセス権を取得します
- `can_approve_pull_request_reviews: true` -- ワークフローによる PR 承認を許可します

### `branch_protection`

ブランチ保護ルールの配列。各エントリは `branch` 名と目的の保護設定を指定します。現在、`main` のみが保護されています。

主要フィールド:

- `enforce_admins: true` -- 保護ルールはリポジトリ管理者にも適用されます
- `required_status_checks.strict: false` -- マージ前にブランチが最新である必要はありません
- `required_status_checks.contexts` -- ダウンストリームリポジトリが合格しなければならないチェック名（例: `check / Check linked issues` および `lint / Shell Unit Tests`）
- `required_status_checks.self_contexts` -- docs-control 自体が合格しなければならないチェック名（例: `Check linked issues` および `Shell Unit Tests`）
- `required_pull_request_reviews: null` -- PR レビューの承認は不要です
- `restrictions: null` -- ブランチ保護以外のプッシュ制限はありません

#### `contexts` 対 `self_contexts`

ダウンストリームリポジトリが呼び出し元ワークフローを使用する場合、ステータスチェック名は `<caller_job_key> / <reusable_job_name>` になります。例えば、`require-linked-issue.yml` 呼び出し元のジョブキーは `check` であるため、チェック名は `check / Check linked issues` になります。しかし、docs-control が同じワークフローを直接実行する場合（`pull_request_target` トリガー経由）、チェック名は単に `Check linked issues` になります。

`self_contexts` フィールドは、docs-control 自体に適用されるチェック名を保持します。[設定適用](./settings-enforcement/) 中、ワークフローはソースリポジトリで実行されているかどうかを検出し、ブランチ保護を適用する前に `self_contexts` を `contexts` に入れ替えます。`self_contexts` フィールドは、GitHub API にペイロードを送信する前に常に削除されます。

`Shell Unit Tests` は、統一されたリポジトリテストゲートです。再利用可能なワークフローは常にこれを報告します。コンシューマーリポジトリはすべての `tests/test-*.sh` ファイルを実行し、一致するテストがないリポジトリは明示的なテストなしメッセージで成功を報告します。これにより、リポジトリごとのオプトインリストに頼るのではなく、リポジトリのシェルテストがデフォルトで必須になります。

#### コンシューマーシェルテストプロファイル

デフォルトでは、すべてのルートレベルの `tests/test-*.sh` スクリプトが、プロビジョニングされていない GitHub ホストランナー上で閉じた環境（hermetic）であると想定しています。このグロブパターン配下にコンテナまたはサービス統合テストも保存しているリポジトリには、`repo-settings.json` 内に `consumer_shell_tests.profiles` エントリが必要です。

各プロファイルは、一致する完全なインベントリを分類します:

- `unit` エントリには、テストの `path` と `args` 配列が含まれます。ランナーはシェルの評価を行わずに各引数をそのまま渡します。
- `environment` エントリには、テストの `path` と、ベアランナーのユニットゲートで実行できない理由を説明する空でない `reason` が含まれます。

再利用可能なワークフローは、同じ docs-control の `main` リビジョンからセレクターと設定を取得し、そのリビジョンをログに記録し、何も実行する前にインベントリを検証します。設定の不足、不安全なパスや引数、重複するパス、および未分類または不足しているテストは、必須コンテキストを失敗させます。これにより、プロファイルは無視リストではなく、監査された分類契約となります。プロファイルのないリポジトリは、広範なデフォルトを維持します。

`xcsh` のオーバーライドは、そのリポジトリが再利用可能な Super-Linter ワークフローを呼び出さないため、両方の Super-Linter コンテキストを除外します。ネイティブの `check`、`pii-guard`、および `test` コンテキストは引き続き必須です。ライブ検証により、追加前に除外が必要であることが証明されなければなりません。

`paths` または `paths-ignore` フィルタを持つワークフローからのコンテキストを必須にしないでください。ワークフローが開始されない場合、GitHub はそのコンテキストを保留状態のままにします。広範なセキュリティツールは、フィルタリングされていないプルリクエストワークフロー、またはスケジュールされたフルツリー監査で実行する必要があります。管理対象のワークフローセキュリティ監査では、`zizmor` に対して後者のモデルを使用します。スキップされたジョブは引き続き成功したチェックを報告するため、ジョブレベルの条件は安全です。

### `topics`

リポジトリに適用する GitHub トピックの配列。現在空です -- トピックは強制されません。

### `pages`

GitHub Pages の設定:

- `enabled: true` -- 登録されているすべてのリポジトリで Pages が有効になっていることを確認します
- `build_type: "workflow"` -- Pages のビルドに GitHub Actions を使用します（従来のブランチベースのビルドではありません）

### `managed_files`

ファイル同期マニフェストを定義します:

- `source_repo` -- 管理対象ファイルの正規バージョンを保持するリポジトリ（`f5-sales-demo/docs-control`）
- `files` -- docs-control 内のソースパスをダウンストリームリポジトリ内の送信先パスにマッピングする `{src, dest}` オブジェクトの配列

[ファイル同期ワークフロー](./file-sync/) は、この配列を反復処理してドリフトを検出し、修正します。ここにリストされていないファイル（`dependabot.yml` や `README.md` など）は、静的ソースから同期されるのではなく、動的に生成されます。
