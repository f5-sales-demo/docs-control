## Dispatch trigger

When template files change on docs-control's `main` branch, the dispatch workflow at `.github/workflows/dispatch-downstream.yml` triggers enforcement in every enrolled downstream repository.

The trigger paths include:

- `.github/config/repo-settings.json`, `downstream-repos.json`, `docs-sites.json`
- `workflows/**` (caller templates)
- `.github/workflows/enforce-repo-settings.yml`, `sync-managed-files.yml`, `github-pages-deploy.yml`, `require-linked-issue.yml`
- `.github/PULL_REQUEST_TEMPLATE.md`, `.github/ISSUE_TEMPLATE/**`
- `CONTRIBUTING.md`, `CLAUDE.md`, `.editorconfig`, `.gitignore`, `LICENSE`, `.pre-commit-config.yaml`, `README.md.tpl`

The workflow verifies that its receipt is current protected `main` and that the
immutable caller pin contains the exact reusable implementation. It then reads
the downstream repository list and calls `gh workflow run
enforce-repo-settings.yml -f source_sha=<receipt>` for each repository using the
`REPO_SETTINGS_TOKEN` secret, with 3 retry attempts per repository. Historical
main receipts defer; unmerged receipts fail provenance validation.

## Caller workflow templates

The `workflows/` directory is the source of truth for downstream caller files.
Every reusable workflow reference in those callers is an immutable commit pin.
Resolve protected `main` once, then download caller bytes at that exact receipt:

```bash
revision=$(gh api repos/f5-sales-demo/docs-control/commits/main --jq '.sha')
for workflow in enforce-repo-settings github-pages-deploy require-linked-issue; do
  gh api \
    "repos/f5-sales-demo/docs-control/contents/workflows/${workflow}.yml?ref=${revision}" \
    --jq '.content' | base64 -d > ".github/workflows/${workflow}.yml"
done
```

The governed sync installs the complete caller set automatically. The three
files below illustrate the main enforcement, Pages, and pull-request gates.

### enforce-repo-settings.yml

Calls both `enforce-repo-settings.yml` and `sync-managed-files.yml` as parallel jobs with separate tokens. Triggers on schedule (every 6 hours), push to `.github/config/**`, and manual dispatch.

The caller resolves one protected-main receipt for scheduled and push runs. A
manual run must supply `source_sha`. Both reusable jobs receive that same
receipt. Before either job starts, the caller proves its own live blob and both
immutable reusable-workflow pins against current protected main.

During an implementation transition, `.github/config/governance-rollout.json`
sets the fleet to `quiesced`. The dispatcher disables downstream enforcement,
cancels active legacy runs, and installs the exact caller through one-file PRs.
The `sync/exact-caller-*` branch namespace is reserved for that monotonic
bootstrap; complete paginated PR inventory ensures a later run cannot be
overtaken, and superseded PR branches are deleted rather than force-updated.
The later exact-read release changes the state to `active`; enforcement resumes
only after every caller and reusable pin is measured at the artifacts.

Governed pin updates use a unique branch for each workflow run. The
`sync/governed-workflow-pins-*` namespace is reserved exclusively for this
monotonic automation: it inventories every open automation pull request and
matching remote ref, then deletes superseded owners without force-updating
them. The updater proves that its commit is based
on current protected `main`, verifies the exact pull-request base, head, history,
and files, and enables auto-merge only while required status checks are strict
(the branch must be up to date before GitHub can merge it).

### github-pages-deploy.yml

Calls the reusable docs build and deploy workflow. Triggers on push to `docs/**` on main and manual dispatch.

The caller deploys documentation from an immutable reusable-workflow pin. It
triggers on configured documentation paths and on manual dispatch.

### require-linked-issue.yml

Calls the reusable linked-issue check workflow. Triggers on `pull_request_target` events.

The caller invokes the immutable linked-issue implementation for
`pull_request_target` events and grants only issue-read and pull-request-write
permissions.

## Check name format

When a downstream repository uses a caller workflow, the GitHub Actions status check name becomes `<caller_job_key> / <reusable_job_name>`. For example:

| Caller job key | Reusable job name | Resulting check name |
|---|---|---|
| `check` | `Check linked issues` | `check / Check linked issues` |
| `lint` | `Lint Code Base` | `lint / Lint Code Base` |
| `lint` | `Shell Unit Tests` | `lint / Shell Unit Tests` |

This is why docs-control's [configuration](./configuration/) has both `contexts` (for downstream repositories) and `self_contexts` (for docs-control itself) -- the check names differ depending on whether the workflow runs directly or through a caller.

## PR quality gate

The `require-linked-issue.yml` caller enforces that every PR is linked to a GitHub issue. PRs from automated branches (`dependabot/**`, `governance/**`, `sync/**`, etc.) are excluded.
