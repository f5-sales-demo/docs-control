## การอ้างอิงฟิลด์ (Field reference)

### `repository`

การตั้งค่าคลังเก็บข้อมูล GitHub มาตรฐานที่ปรับใช้ผ่าน `PATCH /repos/{owner}/{repo}` แต่ละคีย์แมปโดยตรงกับฟิลด์ GitHub API [workflow การบังคับใช้](./settings-enforcement/) จะเปรียบเทียบแต่ละคีย์กับค่าปัจจุบันของคลังเก็บข้อมูล และปรับใช้เฉพาะคีย์ที่มีการเปลี่ยนแปลงเท่านั้น

การตั้งค่าที่สำคัญ:

- `delete_branch_on_merge: true` -- ลบสาขา PR ที่รวมแล้วโดยอัตโนมัติ
- `allow_update_branch: true` -- เปิดใช้งานปุ่ม "Update branch" บน PRs
- `homepage: ""` -- คำนวณโดยอัตโนมัติ ณ เวลาทำงานเป็น `https://f5-sales-demo.github.io/{repo}/`

### `actions_permissions`

ควบคุมสิทธิ์ GitHub Actions workflow สำหรับคลังเก็บข้อมูล:

- `default_workflow_permissions: "write"` -- workflows ได้รับสิทธิ์อ่าน/เขียนไปยังคลังเก็บข้อมูลโดยเริ่มต้น
- `can_approve_pull_request_reviews: true` -- อนุญาตให้ workflows อนุมัติ PRs

### `branch_protection`

อาร์เรย์ของกฎการป้องกันสาขา แต่ละรายการระบุชื่อ `branch` และการตั้งค่าการป้องกันที่ต้องการ ปัจจุบันมีการป้องกันเฉพาะ `main` เท่านั้น

ฟิลด์หลัก:

- `enforce_admins: true` -- กฎการป้องกันบังคับใช้กับผู้ดูแลระบบคลังเก็บข้อมูลด้วย
- `required_status_checks.strict: false` -- สาขาไม่จำเป็นต้องเป็นปัจจุบันที่สุดก่อนการรวม
- `required_status_checks.contexts` -- ชื่อการตรวจสอบที่คลังเก็บข้อมูลปลายน้ำต้องผ่าน (เช่น `check / Check linked issues` และ `lint / Shell Unit Tests`)
- `required_status_checks.self_contexts` -- ชื่อการตรวจสอบที่ docs-control เองต้องผ่าน (เช่น `Check linked issues` และ `Shell Unit Tests`)
- `required_pull_request_reviews: null` -- ไม่ต้องมีการอนุมัติการรีวิว PR
- `restrictions: null` -- ไม่มีข้อจำกัดการ push นอกเหนือจากการป้องกันสาขา

#### `contexts` vs `self_contexts`

เมื่อคลังเก็บข้อมูลปลายน้ำใช้ caller workflow ชื่อการตรวจสอบสถานะจะกลายเป็น `<caller_job_key> / <reusable_job_name>` ตัวอย่างเช่น caller `require-linked-issue.yml` มีคีย์งานเป็น `check` ดังนั้นชื่อการตรวจสอบจะเป็น `check / Check linked issues` แต่เมื่อ docs-control รัน workflow เดียวกันโดยตรง (ผ่านตัวจุดชนวน `pull_request_target`) ชื่อการตรวจสอบจะเป็นเพียง `Check linked issues`

ฟิลด์ `self_contexts` จะเก็บชื่อการตรวจสอบที่นำไปใช้กับ docs-control เอง ระหว่าง [การบังคับใช้](./settings-enforcement/) workflow จะตรวจจับว่ากำลังรันบนคลังเก็บข้อมูลต้นทางหรือไม่ และสลับ `self_contexts` เข้าไปใน `contexts` ก่อนปรับใช้การป้องกันสาขา ฟิลด์ `self_contexts` จะถูกตัดออกเสมอก่อนส่งเนื้อหาข้อมูลไปยัง GitHub API

`Shell Unit Tests` คือด่านตรวจการทดสอบคลังเก็บข้อมูลที่เป็นแบบเดียวกัน workflow ที่นำกลับมาใช้ใหม่ได้จะรายงานเสมอ: คลังเก็บข้อมูลผู้ใช้จะรันทุกไฟล์ `tests/test-*.sh` ในขณะที่คลังเก็บข้อมูลที่ไม่มีการทดสอบที่ตรงกันจะรายงานความสำเร็จพร้อมข้อความแจ้งว่าไม่มีการทดสอบ สิ่งนี้ทำให้การทดสอบเชลล์ของคลังเก็บข้อมูลเป็นสิ่งจำเป็นโดยเริ่มต้น แทนที่จะพึ่งพารายการเลือกเข้าร่วมของแต่ละคลังเก็บข้อมูล

#### โปรไฟล์การทดสอบเชลล์ของผู้ใช้ (Consumer shell-test profiles)

ค่าเริ่มต้นสมมติว่าสคริปต์ `tests/test-*.sh` ระดับรากทุกสคริปต์ทำงานแบบแยกขาด (hermetic) บน GitHub-hosted runner คลังเก็บข้อมูลที่จัดเก็บการทดสอบการรวมระบบของคอนเทนเนอร์หรือบริการภายใต้ glob นั้นด้วย จำเป็นต้องมีรายการ `consumer_shell_tests.profiles` ใน `repo-settings.json`

แต่ละโปรไฟล์จะจัดหมวดหมู่รายการที่ตรงกันทั้งหมด:

- รายการ `unit` ประกอบด้วย `path` ของการทดสอบและอาร์เรย์ `args` runner จะส่งผ่านแต่ละอาร์กิวเมนต์ตามตัวอักษรโดยไม่มีการประเมินเชลล์
- รายการ `environment` ประกอบด้วย `path` ของการทดสอบและ `reason` ที่ไม่ว่างเปล่าอธิบายว่าเหตุใดด่านตรวจหน่วยของ bare-runner จึงไม่สามารถประมวลผลได้

workflow ที่นำกลับมาใช้ใหม่ได้จะดึงตัวเลือกและการกำหนดค่าจากซอร์สโค้ด `main` เดียวกันของ docs-control บันทึกซอร์สโค้ดนั้น และตรวจสอบรายการก่อนรันสิ่งใดๆ การกำหนดค่าที่สูญหาย เส้นทางหรืออาร์กิวเมนต์ที่ไม่ปลอดภัย เส้นทางที่ซ้ำกัน และการทดสอบที่ไม่ได้จัดหมวดหมู่หรือสูญหาย จะทำให้บริบทที่จำเป็นล้มเหลว สิ่งนี้ทำให้โปรไฟล์เป็นสัญญาการจัดหมวดหมู่ที่ได้รับการตรวจสอบแล้ว ไม่ใช่รายการละเว้น คลังเก็บข้อมูลที่ไม่มีโปรไฟล์จะคงค่าเริ่มต้นแบบกว้างไว้

การเขียนทับ `xcsh` จะยกเว้นบริบท Super-Linter ทั้งสอง เนื่องจากคลังเก็บข้อมูลนั้นไม่ได้เรียกใช้ Super-Linter workflow ที่นำกลับมาใช้ใหม่ได้ บริบทดั้งเดิม `check`, `pii-guard` และ `test` ยังคงเป็นสิ่งจำเป็น การยืนยันสดต้องพิสูจน์ว่าจำเป็นต้องยกเว้นก่อนที่จะเพิ่มเข้ามา

อย่ากำหนดให้บริบทจาก workflow ที่มีตัวกรอง `paths` หรือ `paths-ignore` เป็นสิ่งจำเป็น GitHub จะทิ้งบริบทนั้นไว้ในสถานะรอนานเมื่อ workflow ไม่เริ่มทำงาน เครื่องมือความปลอดภัยแบบกว้างต้องรันใน pull-request workflow ที่ไม่มีตัวกรอง หรือในการตรวจสอบผังต้นไม้เต็มรูปแบบตามกำหนดเวลา การตรวจสอบความปลอดภัย workflow ที่อยู่ในการดูแลใช้โมเดลหลังสำหรับ `zizmor` เงื่อนไขระดับงานนั้นปลอดภัยเนื่องจากงานที่ถูกข้ามยังคงรายงานการตรวจสอบที่สำเร็จ

### `topics`

อาร์เรย์ของหัวข้อ GitHub ที่จะปรับใช้กับคลังเก็บข้อมูล ปัจจุบันว่างเปล่า -- ไม่มีการบังคับใช้หัวข้อ

### `pages`

การกำหนดค่า GitHub Pages:

- `enabled: true` -- มั่นใจว่าเปิดใช้งาน Pages ในทุกคลังเก็บข้อมูลที่ลงทะเบียน
- `build_type: "workflow"` -- ใช้ GitHub Actions สำหรับการบิลด์ Pages (ไม่ใช่การบิลด์ตามสาขาแบบเก่า)

### `managed_files`

นิยามรายการซิงโครไนซ์ไฟล์:

- `source_repo` -- คลังเก็บข้อมูลที่เก็บเวอร์ชันหลักของไฟล์ที่อยู่ในการดูแล (`f5-sales-demo/docs-control`)
- `files` -- อาร์เรย์ของวัตถุ `{src, dest}` ที่แมปเส้นทางต้นทางใน docs-control ไปยังเส้นทางปลายทางในคลังเก็บข้อมูลปลายน้ำ

[file sync workflow](./file-sync/) จะวนซ้ำอาร์เรย์นี้เพื่อตรวจจับและแก้ไขการเปลี่ยนแปลง (drift) ไฟล์ที่ไม่ได้ระบุไว้ที่นี่ (เช่น `dependabot.yml` และ `README.md`) จะถูกสร้างขึ้นแบบไดนามิกมากกว่าการซิงค์จากแหล่งสแตติก
