## 字段参考

### `repository`

通过 `PATCH /repos/{owner}/{repo}` 应用的标准 GitHub 存储库设置。每个键直接映射到 GitHub API 字段。[强制执行工作流](./settings-enforcement/) 将每个键与存储库的当前值进行比较，仅对发生漂移的键进行补丁修改。

显著设置：

- `delete_branch_on_merge: true` -- 合并 PR 分支后自动清理该分支
- `allow_update_branch: true` -- 在 PR 上启用 "Update branch" 按钮
- `homepage: ""` -- 在运行时自动计算为 `https://f5-sales-demo.github.io/{repo}/`

### `actions_permissions`

控制存储库的 GitHub Actions 工作流权限：

- `default_workflow_permissions: "write"` -- 工作流默认获得存储库的读/写访问权限
- `can_approve_pull_request_reviews: true` -- 允许工作流批准 PR

### `branch_protection`

分支保护规则数组。每个条目指定一个 `branch` 名称和期望的保护设置。目前仅保护 `main`。

关键字段：

- `enforce_admins: true` -- 保护规则同样适用于存储库管理员
- `required_status_checks.strict: false` -- 分支在合并前不需要保持最新状态
- `required_status_checks.contexts` -- 下游存储库必须通过的检查名称（例如 `check / Check linked issues` 和 `lint / Shell Unit Tests`）
- `required_status_checks.self_contexts` -- docs-control 本身必须通过的检查名称（例如 `Check linked issues` 和 `Shell Unit Tests`）
- `required_pull_request_reviews: null` -- 不需要 PR 审查批准
- `restrictions: null` -- 除分支保护外无推送限制

#### `contexts` 与 `self_contexts`

当下游存储库使用调用方工作流时，状态检查名称变为 `<caller_job_key> / <reusable_job_name>`。例如，`require-linked-issue.yml` 调用方的任务键为 `check`，因此检查名称为 `check / Check linked issues`。但当 docs-control 直接运行相同的工作流（通过 `pull_request_target` 触发器）时，检查名称仅为 `Check linked issues`。

`self_contexts` 字段存储适用于 docs-control 本身的检查名称。在[强制执行](./settings-enforcement/)期间，工作流检测其是否在源存储库上运行，并在应用分支保护之前将 `self_contexts` 替换到 `contexts` 中。在将 Payload 发送到 GitHub API 之前，`self_contexts` 字段总是会被剥离。

`Shell Unit Tests` 是统一的存储库测试门控。可重用工作流始终报告它：使用方存储库运行每个 `tests/test-*.sh` 文件，而没有匹配测试的存储库则报告成功并附带明确的无测试消息。这使得存储库 shell 测试默认成为必需项，而不是依赖于每个存储库的显式选择列表。

#### 使用方 shell 测试 Profile

默认假设每个根目录下的 `tests/test-*.sh` 脚本在未预配置的 GitHub 托管 runner 上都是密封独立的。在改 Glob 下还存储了容器或服务集成测试的存储库需要在 `repo-settings.json` 中添加 `consumer_shell_tests.profiles` 条目。

每个 Profile 对完整的匹配清单进行分类：

- `unit` 条目包含测试 `path` 和 `args` 数组。Runner 字面传递每个参数，不进行 shell 计算。
- `environment` 条目包含测试 `path` 和非空的 `reason`，解释为什么裸 runner 单元门控无法执行它。

可重用工作流从相同的 docs-control `main` 版本获取选择器和配置，记录该版本，并在运行任何内容之前验证清单。缺少配置、不安全的路径或参数、重复的路径以及未分类或缺失的测试都会导致必需的 Context 失败。这使得 Profile 成为经过审计的分类契约，而不是忽略列表。没有 Profile 的存储库保留广泛的默认设置。

`xcsh` 覆盖排除了两个 Super-Linter context，因为该存储库未调用可重用 Super-Linter 工作流；其原生 `check`、`pii-guard` 和 `test` context 仍保持必需状态。在添加排除项之前，实时验证必须证明排除是必要的。

请勿要求带有 `paths` 或 `paths-ignore` 过滤器的工作流中的 context。当工作流未启动时，GitHub 会保持该 context 处于 pending 状态。广泛的安全工具必须在未过滤的拉取请求工作流或计划的全树审计中运行；托管的工作流安全审计为 `zizmor` 使用后一种模型。Job 级别的条件是安全的，因为跳过的 Job 仍会报告成功的检查。

### `topics`

要应用到存储库的 GitHub topic 数组。目前为空 -- 未强制执行 topic。

### `pages`

GitHub Pages 配置：

- `enabled: true` -- 确保在每个已注册的存储库上启用 Pages
- `build_type: "workflow"` -- 使用 GitHub Actions 进行 Pages 构建（而非传统的基于分支的构建）

### `managed_files`

定义文件同步清单：

- `source_repo` -- 保存托管文件规范版本的存储库（`f5-sales-demo/docs-control`）
- `files` -- 一个 `{src, dest}` 对象数组，将 docs-control 中的源路径映射到下游存储库中的目标路径

[文件同步工作流](./file-sync/) 迭代此数组以检测并纠正漂移。未在此处列出的文件（如 `dependabot.yml` 和 `README.md`）是动态生成的，而不是从静态源同步的。
