## مرجع الحقول

### `repository`

إعدادات مستودع GitHub القياسية المطبقة عبر `PATCH /repos/{owner}/{repo}`. يترجم كل مفتاح مباشرة إلى حقل في API الخاصة بـ GitHub. يقارن [سير عمل الإنفاذ](./settings-enforcement/) كل مفتاح بالقيمة الحالية للمستودع ويقوم بإصلاح المفاتيح المنحرفة فقط.

إعدادات بارزة:

- `delete_branch_on_merge: true` -- ينظف تلقائياً فروع طلبات السحب المدمجة
- `allow_update_branch: true` -- يُمكّن زر "Update branch" في طلبات السحب
- `homepage: ""` -- يُحسب تلقائياً في وقت التشغيل كـ `https://f5-sales-demo.github.io/{repo}/`

### `actions_permissions`

يتحكم في صلاحيات سير عمل GitHub Actions للمستودع:

- `default_workflow_permissions: "write"` -- تحصل مسارات العمل على وصول قراءة/كتابة للمستودع افتراضياً
- `can_approve_pull_request_reviews: true` -- يسمح لمسارات العمل بالموافقة على طلبات السحب

### `branch_protection`

مصفوفة من قواعد حماية الفروع. تُحدد كل إدخالة اسم `branch` وإعدادات الحماية المطلوبة. حالياً فقط `main` محمي.

الحقول الرئيسية:

- `enforce_admins: true` -- تنطبق قواعد الحماية على مسؤولي المستودع أيضاً
- `required_status_checks.strict: false` -- لا يلزم تحديث الفروع قبل الدمج
- `required_status_checks.contexts` -- أسماء الفحوصات التي يجب أن تجتازها المستودعات التابعة (على سبيل المثال، `check / Check linked issues` و `lint / Shell Unit Tests`)
- `required_status_checks.self_contexts` -- أسماء الفحوصات التي يجب أن يجتازها docs-control نفسه (على سبيل المثال، `Check linked issues` و `Shell Unit Tests`)
- `required_pull_request_reviews: null` -- لا يلزم الحصول على موافقة مراجعة طلب السحب
- `restrictions: null` -- لا توجد قيود دفع بخلاف حماية الفروع

#### `contexts` مقابل `self_contexts`

عندما يستخدم مستودع تابع سير عمل مستدعٍ، يصبح اسم فحص الحالة `<caller_job_key> / <reusable_job_name>`. على سبيل المثال، يمتلك المستدعي `require-linked-issue.yml` مفتاح المهمة `check`، لذا فإن اسم الفحص هو `check / Check linked issues`. ولكن عندما يُشغل docs-control نفس سير العمل مباشرة (عبر مشغل `pull_request_target`)، فإن اسم الفحص يكون مجرد `Check linked issues`.

يخزن الحقل `self_contexts` أسماء الفحوصات التي تنطبق على docs-control نفسه. أثناء [الإنفاذ](./settings-enforcement/)، يكتشف سير العمل ما إذا كان يعمل على المستودع المصدر ويستبدل `self_contexts` بـ `contexts` قبل تطبيق حماية الفروع. يُجرد الحقل `self_contexts` دائماً قبل إرسال البيانات إلى GitHub API.

`Shell Unit Tests` هو بوابة اختبار المستودع الموحدة. يبلغ سير العمل القابل لإعادة الاستخدام دائماً عنها: تشغل المستودعات المستهلكة كل ملف `tests/test-*.sh`، بينما يبلغ المستودع الذي لا يحتوي على اختبارات مطابقة عن النجاح مع رسالة صريحة بعدم وجود اختبارات. هذا يجعل اختبارات Shell للمستودع مطلوبة افتراضياً بدلاً من الاعتماد على قوائم الاشتراك لكل مستودع.

#### ملفات تعريف اختبارات shell للمستهلك

يفترض الافتراضي أن كل برنامج نصي `tests/test-*.sh` على مستوى الجذر مستقل على مشغل مستضاف في GitHub بدون إعداد مسبق. يحتاج المستودع الذي يخزن أيضاً اختبارات تكامل الحاويات أو الخدمات تحت ذلك النمط إلى إدخال `consumer_shell_tests.profiles` في `repo-settings.json`.

يصنف كل ملف تعريف المخزون المكتمل بالكامل:

- تحتوي إدخالات `unit` على `path` الاختبار ومصفوفة `args`. يمرر المشغل كل وسيط حرفياً دون تقييم shell.
- تحتوي إدخالات `environment` على `path` الاختبار و `reason` غير فارغ يوضح سبب عدم قدرة بوابة الوحدة البسيطة على تنفيذه.

يجلب سير العمل القابل لإعادة الاستخدام المحدد والتكوين من نفس مراجعة `main` لـ docs-control، ويسجل تلك المراجعة، ويتحقق من صحة المخزون قبل تشغيل أي شيء. التكوين المفقود، أو المسارات أو الوسائط غير الآمنة، أو المسارات المكررة، والاختبارات غير المصنفة أو المفقودة تُفشل السياق المطلوب. هذا يجعل ملف التعريف عقداً مدققاً للتصنيف بدلاً من قائمة تجاهل. تحتفظ المستودعات التي لا تمتلك ملف تعريف بالافتراضي العام.

يستبعد تجاوز `xcsh` كلا سياقي Super-Linter لأن هذا المستودع لا يستدعي سير عمل Super-Linter القابل لإعادة الاستخدام؛ وتظل سياقاته الأصلية `check` و `pii-guard` و `test` مطلوبة. يجب أن يثبت التحقق المباشر أن الاستثناء ضروري قبل إضافته.

لا تتطلب سياقاً من سير عمل يحتوي على تصفية `paths` أو `paths-ignore`. يترك GitHub هذا السياق معلقاً عندما لا يبدأ سير العمل. يجب أن تعمل أدوات الأمن الشاملة في سير عمل طلب سحب غير مصفى أو في تدقيق شجرة كامل مجدول؛ يستخدم تدقيق أمان سير العمل المدار النموذج الأخير لـ `zizmor`. تعتبر الحالة على مستوى المهمة آمنة لأن المهمة المتخطاة تظل تبلغ عن فحص ناجح.

### `topics`

مصفوفة من مواضيع GitHub لتطبيقها على المستودع. حالياً فارغة -- لا يتم إنفاذ المواضيع.

### `pages`

تكوين GitHub Pages:

- `enabled: true` -- يضمن تمكين Pages في كل مستودع مسجل
- `build_type: "workflow"` -- يستخدم GitHub Actions لبناء Pages (وليس البناء القديم القائم على الفروع)

### `managed_files`

يحدد بيان مزامنة الملفات:

- `source_repo` -- المستودع الذي يحمل النسخ المعتمدة للملفات المدارة (`f5-sales-demo/docs-control`)
- `files` -- مصفوفة من كائنات `{src, dest}` تربط مسارات المصدر في docs-control بمسارات الوجهة في المستودعات التابعة

يتنقل [سير عمل مزامنة الملفات](./file-sync/) عبر هذه المصفوفة لاكتشاف الانحراف وتصحيحه. الملفات غير المدرجة هنا (مثل `dependabot.yml` و `README.md`) يتم إنشاؤها ديناميكياً بدلاً من المزامنة من مصادر ثابتة.
