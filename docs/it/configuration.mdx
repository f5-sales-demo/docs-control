## Riferimento dei campi

### `repository`

Impostazioni standard del repository GitHub applicate tramite `PATCH /repos/{owner}/{repo}`. Ogni chiave mappa direttamente sul campo dell'API GitHub. Il [workflow di enforcement](./settings-enforcement/) confronta ciascuna chiave con il valore attuale del repository e applica la patch solo alle chiavi che hanno subito un disallineamento.

Impostazioni rilevanti:

- `delete_branch_on_merge: true` -- elimina automaticamente le branch delle PR sottoposte a merge
- `allow_update_branch: true` -- abilita il pulsante "Update branch" sulle PR
- `homepage: ""` -- calcolato automaticamente a runtime come `https://f5-sales-demo.github.io/{repo}/`

### `actions_permissions`

Controlla i permessi dei workflow di GitHub Actions per il repository:

- `default_workflow_permissions: "write"` -- i workflow ottengono l'accesso di lettura/scrittura al repository per impostazione predefinita
- `can_approve_pull_request_reviews: true` -- consente ai workflow di approvare le PR

### `branch_protection`

Un array di regole di protezione dei branch. Ogni voce specifica un nome di `branch` e le impostazioni di protezione desiderate. Attualmente solo `main` è protetto.

Campi chiave:

- `enforce_admins: true` -- le regole di protezione si applicano anche agli amministratori del repository
- `required_status_checks.strict: false` -- le branch non devono necessariamente essere aggiornate prima del merge
- `required_status_checks.contexts` -- i nomi dei controlli che i repository downstream devono superare (ad esempio, `check / Check linked issues` e `lint / Shell Unit Tests`)
- `required_status_checks.self_contexts` -- i nomi dei controlli che docs-control stesso deve superare (ad esempio, `Check linked issues` e `Shell Unit Tests`)
- `required_pull_request_reviews: null` -- nessuna approvazione di revisione PR richiesta
- `restrictions: null` -- nessuna restrizione di push oltre alla protezione dei branch

#### `contexts` rispetto a `self_contexts`

Quando un repository downstream utilizza un workflow chiamante, il nome del controllo di stato diventa `<caller_job_key> / <reusable_job_name>`. Ad esempio, il chiamante `require-linked-issue.yml` ha la chiave job `check`, quindi il nome del controllo è `check / Check linked issues`. Ma quando docs-control esegue lo stesso workflow direttamente (tramite il trigger `pull_request_target`), il nome del controllo è semplicemente `Check linked issues`.

Il campo `self_contexts` memorizza i nomi dei controlli che si applicano a docs-control stesso. Durante l'[enforcement](./settings-enforcement/), il workflow rileva se è in esecuzione sul repository sorgente e scambia `self_contexts` in `contexts` prima di applicare la protezione dei branch. Il campo `self_contexts` viene sempre rimosso prima di inviare il payload all'API GitHub.

`Shell Unit Tests` è il gate uniforme di test del repository. Il workflow riutilizzabile lo segnala sempre: i repository consumatori eseguono ogni file `tests/test-*.sh`, mentre un repository senza test corrispondenti segnala il successo con un messaggio esplicito di assenza di test. Ciò rende i test shell del repository richiesti per impostazione predefinita invece di affidarsi a liste di opt-in per repository.

#### Profili shell-test del consumatore

L'impostazione predefinita presuppone che ogni script `tests/test-*.sh` a livello radice sia ermetico su un runner ospitato su GitHub non fornito. Un repository che memorizza anche test di integrazione di container o servizi sotto quel glob necessita di una voce `consumer_shell_tests.profiles` in `repo-settings.json`.

Ogni profilo classifica l'inventario corrispondente completo:

- Le voci `unit` contengono un `path` di test e un array `args`. Il runner passa ogni argomento letteralmente, senza valutazione dello shell.
- Le voci `environment` contengono un `path` di test e una `reason` non vuota che spiega perché il gate unitario sul runner semplice non può eseguirlo.

Il workflow riutilizzabile recupera il selettore e la configurazione dalla stessa revisione `main` di docs-control, registra tale revisione e valida l'inventario prima di eseguire qualsiasi cosa. Configurazione mancante, percorsi o argomenti non sicuri, percorsi duplicati e test non classificati o mancanti fanno fallire il contesto richiesto. Ciò rende un profilo un contratto di classificazione controllato anziché una lista di ignorati. I repository senza un profilo mantengono l'impostazione predefinita generale.

L'override `xcsh` esclude entrambi i contesti di Super-Linter perché quel repository non chiama il workflow riutilizzabile di Super-Linter; i suoi contesti nativi `check`, `pii-guard` e `test` rimangono richiesti. La verifica dal vivo deve dimostrare che un'esclusione è necessaria prima che venga aggiunta.

Non richiedere un contesto da un workflow con filtri `paths` o `paths-ignore`. GitHub lascia quel contesto in sospeso quando il workflow non si avvia. Gli strumenti di sicurezza generali devono essere eseguiti in un workflow di pull request non filtrato o in un audit completo programmato; l'audit di sicurezza del workflow gestito utilizza quest'ultimo modello per `zizmor`. Una condizione a livello di job è sicura perché un job ignorato segnala comunque un controllo riuscito.

### `topics`

Un array di argomenti GitHub da applicare al repository. Attualmente vuoto -- gli argomenti non sono applicati.

### `pages`

Configurazione di GitHub Pages:

- `enabled: true` -- assicura che Pages sia abilitato su ogni repository iscritto
- `build_type: "workflow"` -- utilizza GitHub Actions per la build di Pages (non build legacy basate su branch)

### `managed_files`

Definisce il manifesto di sincronizzazione dei file:

- `source_repo` -- il repository que contiene le versioni canoniche dei file gestiti (`f5-sales-demo/docs-control`)
- `files` -- un array di oggetti `{src, dest}` che mappano i percorsi sorgente in docs-control con i percorsi di destinazione nei repository downstream

Il [workflow di sincronizzazione file](./file-sync/) cicla su questo array per rilevare e correggere i disallineamenti. I file non elencati qui (come `dependabot.yml` e `README.md`) vengono generati dinamicamente anziché sincronizzati da sorgenti statiche.
